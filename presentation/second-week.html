01
What was the problem?

A service that forgets what it already did

The order is three dependent steps — reserve inventory → charge payment → arrange shipping. Nothing about that is hard when everything works. The trouble starts when the process dies in the middle, because the steps have real external side effects that cannot be undone by restarting the program.

Order #1042

Noise-cancelling headphones

$49.50
  • 1 Reserve one unit in the warehouse
  • 2 Charge the customer's card
  • 3 Create a shipment with tracking

A simple order service keeps the order in a local variable: reservationId, paymentId, shipmentId. That works — until the machine running it loses power between step 2 and step 3.

At that moment the state in RAM is gone, but the charge at the payment provider and the reservation in the warehouse are still real. Now the customer retries the checkout. The service has no memory of the first attempt, so it reserves stock again and charges the card a second time.

This is not a rare edge case. Any durable system must assume at-least-once execution: work may be attempted more than once. Without a stable identity for an operation, at-least-once becomes "charged twice".

02
What we suggest as a solution?

Make the database the source of truth

We replace the fragile in-memory flow with a durable workflow engine. It writes every transition to SQLite before it acts, gives each step a stable idempotency key, leases work to workers, and — when a step fails permanently — undoes the earlier steps in reverse order. The one-sentence difference

The naive service asks "what did I just do?" and answers from memory. The engine asks "what is committed?" and answers from disk. Once state is durable and every external call carries a stable key, retries and crashes become ordinary control flow instead of data loss.

    Under the hood

    Seven mechanisms, one guarantee

    The animation above is driven by the same rules as the code in src/engine/. Here is what each mechanism actually does, with a short excerpt of the real implementation.

    01 / DURABILITY

    Write first, act second

    SQLite in WAL mode holds the run, steps, attempts, and an append-only event log. A worker inserts the claim, the attempt row, and the events in one transaction before the handler runs. If the process dies, the next worker reads the same truth. 

    PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
-- claim + attempt + event: one transaction
    02 / STEPS

    The unit of work

    A step is a row with status, attempts, lease, retry policy, idempotency key, and output. claimNext() only returns a pending step whose previous step succeeded — or a compensation whose later compensations are already done. Ordering lives in SQL, not in a call stack. 

    WHERE s.status = 'pending'
  AND s.next_attempt_at <= now
  AND previous.status = 'succeeded'
    03 / IDEMPOTENCY

    Same key, same effect

    Every step gets a stable key when the run is created. Downstream services store effects by that key, so replaying a step returns the original charge or reservation instead of creating a new one. Compensation gets its own suffixed key. 

    execute:  <runId>:<index>:<stepName>
compensate: <runId>:<index>:<stepName>:compensate
    04 / LEASES

    No orphaned steps

    A claim sets lease_owner and lease_expires_at. Other workers ignore the step until the lease expires. On expiry, recovery marks the interrupted attempt lease_expired and puts the step back to pending — any worker may then pick it up. 

    recoverExpiredLeases(now)
  → attempt.status = 'lease_expired'
  → step.status = 'pending'
    05 / FENCING

    Stale results cannot corrupt state

    A worker that lost its lease may still finish its handler. Its completion is a conditional update: if owner or attempt number changed, zero rows are updated and the result is discarded. Only the current lease holder may write success. 

    UPDATE steps SET status = 'succeeded', ...
WHERE id = ? AND status = 'running'
  AND lease_owner = ? AND attempts = ?;
    06 / SAGA

    Undo in reverse order

    A permanent failure marks earlier successful steps pending_compensation. Compensation claims the highest step index first, so a failed shipping step leads to refund → release, never the other way around. A failed compensation leaves a failed run in the audit log. 

    reserve ✓ → pay ✓ → ship ✗
compensate: [pay, reserve]  // reverse
    07 / RETRIES

    Bounded, backed off, visible

    RetryableError and timeouts schedule another attempt with exponential backoff; PermanentError skips straight to compensation. The policy is resolved when the run is created and stored with the step, so a definition change cannot silently alter an in-flight run. 

    { maxAttempts: 4, initialDelayMs: 100,
  maxDelayMs: 2000, backoffFactor: 2 }
// 100ms → 200ms → 400ms → stop
    Concern Naive service Durable engine
    After a crash State is lost; nobody knows what completed. Steps and attempts are on disk; a new worker resumes.
    Retrying a step Creates a second charge and a second reservation. Stable key deduplicates at the payment provider.
    Concurrent workers Both can execute the same step. Atomic claims + leases; stale results are fenced out.
    Permanent failure Half-finished order with a stranded charge. Saga refunds and releases in reverse order.
    Debugging Logs only, no reliable history. Append-only events and a row per attempt.
